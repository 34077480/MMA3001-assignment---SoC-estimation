# AI-use log (factual record for the report's AI reflection)

This is a factual record kept during development, to support the AI-use reflection the brief requires
(section 7). The reflection itself (why AI was used, how it affected your understanding, which decisions
were yours) has to be written by the student; this file only records what happened.

**Tool:** Claude (Anthropic), model Claude Opus 5.5, used through Claude Code (desktop app, agentic mode:
the assistant read files, ran Python and wrote code in this repository).

## What the AI did

* Implemented the student's project plan (Coulomb counting baseline, 1-2 RC ECM + EKF, LSTM; robustness
  tests; FLOP comparison; sensitivity; Pareto trade-off). Added design choices not in the plan, e.g. the
  temperature-dependent OCV, Arrhenius parameters, sensor-corruption scenarios, coverage-constrained
  tuning, beta-NLL loss, input validation.
* Wrote essentially all of the code in `src/`, `scripts/` and `tests/`, ran the experiments and produced
  the figures.
* Diagnosed problems by writing the scripts in `scripts/exploration/`.
* Restructured the repository to meet the brief (package, docstrings, tests, docs, README).

## Decisions made by the student

* Choice of problem and dataset, and the project plan (methods, validation design, robustness tests,
  performance analysis), from the student's proposal; approval by the Unit Coordinator.
* Asked whether closing a memory-hungry application had affected results, which led to the check that
  found the 1 Hz residual-sampling problem (see error 6).
* Asked for the project to be checked against the brief and reworked.
* Chose MIT licence, local git with the student pushing to GitHub, and that the report prose would be
  written by the student from a skeleton.

## Errors, weak suggestions and problems produced by the AI, and how each was caught

| # | What went wrong | How it was caught | Fix |
|---|---|---|---|
| 1 | Built the OCV curve by averaging the C/20 charge and discharge curves (a common textbook trick). On this cell the charge curve sits ~130 mV high, so OCV was biased by ~65 mV. | Validation against relaxed HPPC rest voltages (RMSE 65 mV, figure check) | Level set from relaxed rests; charge curve not used |
| 2 | File-matching pattern let "0degC" match "n10degC", so 0 °C and 10 °C OCV fits silently used -10 °C data: **data leakage from an unseen test temperature**. | Residual table showed identical rows for three temperatures | Anchored regex; regression test `test_file_matching_is_unambiguous` |
| 3 | Left a placeholder (`* 0  # placeholder`) in the OCV slope function. | Noticed on reading the code back | Rewritten |
| 4 | EKF used a separately smoothed dOCV/dSoC that was inconsistent with the interpolated OCV it linearised. | Finite-difference Jacobian test failed (relative error 3.3) | Use the exact slope of the interpolant |
| 5 | First EKF tuning minimised RMSE only: the filter reported σ ≈ 0.05 % while being 1-13 % wrong (3σ coverage ~0 %). | Coverage metric on the test set | Coverage-constrained tuning plus calibration |
| 6 | When the ECM fit ran out of memory, the AI reduced residual sampling to 1 Hz and described the change as harmless without testing it. When re-checked at 5 Hz, cold-temperature SoC RMSE improved by ~0.5 points and parameters became more physical. | The student asked whether the memory problem affected results | 5 Hz made the default; both kept as a documented comparison |
| 7 | Wrote a rough FLOP-count helper before counting properly. | AI flagged it itself before using it | Removed; itemised count in `scripts/perf.py` |
| 8 | Test-design mistakes: a tolerance tighter than accumulated rounding; a test that pushed SoC above 100 %. | Failing tests | Corrected the tests (the code was right) |
| 9 | First LSTM training was unstable (validation RMSE jumping 3-12 %). | Training curve | Lower learning rate, beta-NLL loss, cosine schedule |
| 10 | Left dead code lines in the tuning function twice; left exploration scripts broken after the restructure. | Code reading / running them | Removed / fixed; one script marked historical |
| 11 | The ML model's uncertainty calibration made test coverage *worse* (validation conditions are milder than cold/unseen test conditions). | Coverage metric | Reported as a limitation rather than hidden |

## How AI output was checked

* Every numerical component has an independent check: analytical step response (integrator),
  finite-difference Jacobians, an independent NumPy EKF, synthetic data generated by the model itself,
  charge conservation of the ground truth, OCV against relaxed rests.
* Results were checked against physical expectations (e.g. resistance rising in the cold, OCV
  decreasing with temperature, SoC within [0, 1]).
* A held-out test set (unseen cycles and temperatures) was never used for any decision.
